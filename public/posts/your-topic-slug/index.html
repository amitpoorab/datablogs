    Part 1: Genesis — Why I Built a Data Agent#

    Published: July 30, 2026

    The Problem#

    Picture this: It’s Monday morning. An analyst needs to answer a question for the VP of Sales.

    “How many high-value customers do we have in each region, and what’s the trend over the last quarter?”

    The analyst has three options:

    1. Write SQL from scratch

      • 20 minutes to remember the schema
      • Debug three query errors
      • Wait for results
      • Format into a Slack message

    2. Ask an engineer in Slack

      • Engineer is heads-down on something else
      • Gets the query done in 15 minutes (because they know the schema)
      • Both of you context-switch
      • Creates a dependency chain

    3. Use a BI tool

      • Dashboard exists but doesn’t quite answer the specific question
      • Close enough? Not really.
      • Give up and go back to option 1

    I watched this happen over and over. Smart analysts became stuck in the “query formatting” trap instead of thinking about what the data means.

    The insight: What if they could just ask?

    Analyst: "How many high-value customers by region, last quarter trend?"
Agent: [Finds customer, region, and order tables]
        [Writes the SQL]
        [Validates it's safe]
        [Runs it]
        [Shows results with proof]
        "2,847 high-value customers, up 12% QoQ..."

    No schema memorization. No SQL debuggery. No dependency on an engineer.

    The Opportunity#

    Around the same time, I noticed something shifted: LLMs got really good at tool use.

    Claude 3.5 could reliably:

    • Understand what tools to call
    • Handle multi-turn conversations
    • Use results from one tool to inform the next
    • Explain its reasoning

    But there was a catch. The LLM could also:

    • Hallucinate tables that don’t exist
    • Write inefficient queries
    • Run unbounded queries that blast my database
    • Confidently give wrong answers

    This wasn’t a limitation of the LLM. It was a limitation of how I designed the tools.

    The realization: If I design the tools right, I can give an LLM enough power to be useful and safe.

    The Approach: Three Stages#

    I decided to build this incrementally. Not “everything at once,” but three deliberate stages:

    Stage 1: Metadata Tools (Safe Discovery)#

    Before the agent can write a query, it needs to understand what it has to work with.

    Tools:

    • list_tables() — “What’s available?”
    • describe_table() — “What’s in this table?”

    Why this works: The agent can’t hallucinate tables. It has ground truth. And the analyst can see exactly what the agent saw.

    Stage 2: Safe Query Execution (Guarded Execution)#

    The agent can now inspect the schema and write queries. But queries can:

    • Run forever
    • Blow up memory
    • Delete everything (if I’m not careful)

    So I built a validation layer:

    # Run this before executing ANY query
def validate_sql(sql: str) -> bool:
    # Only SELECT allowed
    if not is_select_query(sql):
        return False
    
    # Auto-inject LIMIT if missing
    if no_limit_clause(sql):
        sql = add_limit(sql, 1000)
    
    # Check tables exist
    for table in extract_tables(sql):
        if table not in warehouse_schema:
            return False
    
    # Check columns exist
    for column in extract_columns(sql):
        if column not in schema[column.table]:
            return False
    
    return True

    Why this works: The agent has enough freedom to be useful, but not enough rope to hang itself.

    Stage 3+: Knowledge & Publishing (Future)#

    • Learn from past queries
    • Cache common results
    • Export and share findings
    • Multi-turn analysis workflows

    (This is the vision. Stage 1-2 is what I’ve shipped so far.)

    Design Decision: Why DuckDB?#

    I evaluated a few options:

    OptionProsCons
    Real production DB (PostgreSQL, Snowflake)Real data, real performance concernsToo risky while building, can’t reset easily
    Pandas + in-memorySimple, no infraDoesn’t scale, won’t teach real lessons
    DuckDBIn-process, fast, TPC-H data, safe to blow awayNot what analysts use in prod

    I chose DuckDB because:

    1. It’s a real SQL engine (lessons transfer to production)
    2. I can generate realistic data (TPC-H benchmark)
    3. It’s safe to experiment — I can reset the database in seconds
    4. The performance characteristics are similar enough to teach real lessons

    The plan: Validate everything on DuckDB, then adapt to production databases later.

    Design Decision: Why Claude Opus?#

    I tested a few models:

    • GPT-4: Works, but expensive and slower
    • Claude 3 Sonnet: Faster, cheaper, but less reliable at complex tool chains
    • Claude 3.5 Opus: Sweet spot of reliability, speed, and cost for this use case

    Claude Opus (now called Claude Opus 4.1) because:

    1. Excellent at reasoning about schemas and SQL
    2. Reliable multi-turn tool use
    3. Doesn’t hallucinate as much when grounded in tool results
    4. Good cost/performance ratio for a production tool

    Design Decision: Why Tool Contracts?#

    I didn’t want to just have tools. I wanted to understand them.

    Every tool in this system declares a ToolContract:

    @dataclass
class ToolContract:
    name: str
    description: str
    
    # 1. When can it be called?
    available: bool
    
    # 2. How trustworthy is the output?
    authority: Literal["canonical", "advisory", "stale"]
    
    # 3. What capability does it provide?
    execution_type: Literal["metadata", "live_data", "sql", "publishing"]
    
    # 4. Who can call it and with what constraints?
    permission_scope: str
    
    # 5. What does it return?
    output_format: str
    
    # 6. Can the user audit the work?
    provides_evidence: bool

    Why? Because when I add a tool, I want to ask:

    • Is this tool available in all contexts, or just some?
    • Can I trust its output, or is it advisory?
    • If something goes wrong, can the user see why?
    • Who should be allowed to call this?

    This prevents me from building tools that look good but are actually problematic.

    The Name: “Data Agent Stack”#

    I’m calling this architectural pattern the Data Agent Stack because it’s layered:

    Layer 1 (Top):    User Conversation → Natural Language
                        ↓
Layer 2:          Claude Opus → Tool Selection & Reasoning
                        ↓
Layer 3:          Tools → SQL/Metadata/Publishing
                        ↓
Layer 4:          Validation → Safety & Constraints
                        ↓
Layer 5 (Bottom): Database → Ground Truth

    Each layer is independent, testable, and can be iterated separately. This is important for both reliability and the evolution of the system.

    What I Learned (Already)#

    1. Tools Are Design Decisions#

    Every tool you add shapes what the LLM can do. A drop_table() tool is a design choice, not a lack of safety. A validate_first wrapper is also a design choice.

    2. Evidence Matters More Than Answers#

    Users don’t just want results. They want to know:

    • What did the agent look at?
    • What tables did it query?
    • What was the query?
    • What was the EXPLAIN plan?

    I spent more time building evidence infrastructure than I expected, but it’s the difference between “I trust this” and “Maybe?”

    3. Multi-Turn Matters#

    The agent is smarter when it can ask clarifying questions:

    • “I found 3 customer tables. Which one?”
    • “Do you mean orders placed OR orders shipped?”
    • “This query will scan 100M rows. Should I add a date filter?”

    Single-turn prompts are weaker than multi-turn conversations.

    4. Incrementalism Wins#

    I could have tried to build Stages 1-2-3 all at once. Instead, I shipped Stage 1 first, tested it, then built Stage 2 on top. This meant:

    • Early feedback (do users actually want metadata discovery?)
    • Simpler debugging (is the problem in my validation or my loop?)
    • Confidence before expanding (Stage 1 works, so I can trust Stage 2)

    5. SQL Validation Is Harder Than It Looks#

    I thought SQL validation would be simple: “just block DROP/DELETE/INSERT.” But the real challenges are:

    • Auto-injecting LIMIT without breaking the query logic
    • Catching subqueries with dangerous operations
    • Validating columns across JOINs and CTEs
    • Giving useful error messages

    This deserves its own blog post (it’s coming in Part 3).

    The Vision#

    In one year, I want analysts to ask the agent questions like:

    “Show me our customer acquisition cost by channel, and flag any channels with CAC > $50. Then tell me which ones have the best retention.”

    And the agent to:

    1. Find the relevant tables (revenue, marketing, retention data)
    2. Write multi-step analysis (CAC calculation → filtering → joining retention)
    3. Show the SQL at each step (so the analyst can verify)
    4. Cache the results (so the next analyst’s question is 10x faster)
    5. Answer follow-up questions (pivot by geography, compare to last quarter, etc.)

    This is Stage 3+. But Stage 1-2 is the foundation.

    What’s Next?#

    I’m currently at Stage 2: The agent can discover schema and run safe queries. The next milestones:

    1. Test Stage 1-2 in the real world — Do analysts actually use this? Or does it feel clunky?
    2. Optimize query performance — Add indexes? Caching? Query rewrite?
    3. Handle edge cases — What breaks in production? (It will break somewhere)
    4. Build Stage 3 — Knowledge tools and publishing

    💭 Reflection#

    Building this project taught me that the bottleneck for AI tools isn’t the LLM. It’s the design of the interfaces around it.

    A well-designed tool (with clear contracts, safety boundaries, and evidence provision) can give an LLM real power without risk.

    A poorly designed tool (with vague permissions, no auditing, and no safety) can fail in invisible ways.

    The Data Agent is my attempt to show what well-designed AI tools look like.
